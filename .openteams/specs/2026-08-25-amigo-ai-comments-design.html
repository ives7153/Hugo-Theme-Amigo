Amigo 朋友圈 AI 角色评论机器人

设计文档 · 2026-08-25 · 状态：设计已与用户确认，待审阅

Go · 零第三方依赖 自建常驻进程 完全伪装 挚友必回 + 活跃度

1. 背景与目标

博客是静态 Hugo（Amigo 主题）+ 自建 Artalk 评论。目标：让多个 AI 角色以"朋友圈好友"身份，拟人化地评论主人的每一条朋友圈——包括互相回复、随机缺席、自然延迟。要求完全伪装，评论中不出现任何 AI 标识，访客看不出是机器人。

核心原则：AI 评论与真人访客评论走完全相同的路径（Artalk 公共评论 API），主题代码零改动。

2. 已确认的决策

  • 部署：自建常驻进程，跑在用户服务器上（与 Artalk 同机），systemd 守护
  • 技术栈：Go，仅标准库，内存约 10~20MB，无供应链风险
  • 伪装程度：完全伪装，无 AI 标识，无可选项开关
  • UI 一致性：主题 UI 与小组件风格零改动——AI 评论完全复用现有 Artalk 渲染（朋友圈评论气泡、头像、时间格式），不新增任何小组件/角标/样式
  • 回复保证：设"挚友"角色（isBestFriend），每帖必回，保证每帖 ≥1 条 AI 回复
  • 活跃度模型：每个角色配置固定活跃度（0~100），按概率独立决定出现/缺席，高频角色稳定出现、低频角色偶尔冒泡，不是纯随机
  • 延迟模型：发帖后每个角色安排随机"刷到时刻"（30 分钟 ~ 24 小时），不秒回
  • AI-AI 互动：上下文驱动——LLM 看到完整评论串自己决定接谁的话；保险丝上限 2 轮，防刷屏
  • 人工评论参与：开启（默认）且可配置开关，AI 以低概率（默认 30%）加入人工评论对话
  • LLM 接口：OpenAI 兼容 chat/completions，请求地址 + API key + 模型名留配置占位，用户自填
  • 防刷屏：每帖软上限（默认 8 条 AI 评论）
  • 状态：本地 JSON 文件持久化，进程重启不丢，全流程幂等去重

3. 架构

博客站点
Hugo / EdgeOne → Artalk 服务器
评论存储 / API ←→ AI 机器人（Go）
同机常驻 → LLM API
OpenAI 兼容
  • 机器人轮询站点 sitemap.xml 发现新帖（Hugo 默认生成）
  • 通过 Artalk 公共 API 拉取评论、发布评论（与真人同路径，无需管理员 token）
  • 帖子正文从帖子 HTML 抓取并去标签（正文 + 文本即可，无需站方特权）

4. 组件划分

组件职责依赖
主循环定时唤醒：检查新帖 → 推进调度 → 处理到期动作无
角色管理器角色列表、活跃度判定、挚友兜底、点赞概率配置
调度器每帖每角色的刷到时刻、缺席判定、cascade 轮次状态存储
上下文组装器把帖子内容 + 评论串 + 角色人设拼成 promptArtalk 客户端
LLM 客户端调用 OpenAI 兼容 chat/completions，超时与失败处理网络
Artalk 客户端GET/POST 评论、按 page_key 查询网络
状态存储ai-state.json 原子读写无

每个组件单职责、可独立测试；LLM 客户端与 Artalk 客户端只依赖 HTTP 接口契约。

5. 配置（config.json）

为保持零第三方依赖，配置用 JSON（Go 标准库可直接解析）。llm 段全部占位，由用户填写。

{
  "artalk": {
    "server": "https://artalk.example.com",
    "site": "my-site"
  },
  "siteUrl": "https://example.com",   // ← 博客站点地址，轮询 sitemap 用
  "llm": {
    "endpoint": "https://api.deepseek.com/v1/chat/completions",
    "apiKey": "sk-xxxx",          // ← 用户自填
    "model": "deepseek-chat"      // ← 用户自填
  },
  "behavior": {
    "checkInterval": "5m",
    "snoozeMin": "30m",
    "snoozeMax": "24h",
    "joinHumanComment": true,
    "joinHumanCommentRate": 0.3,
    "cascadeMaxRounds": 2,
    "maxCommentsPerPost": 8
  },
  "characters": [
    {
      "name": "阿伟",
      "email": "awei@example.com",
      "avatar": "",
      "persona": "毒舌但嘴硬心软的老友，爱损人但句句在理",
      "activity": 100,
      "likeRate": 0.2,
      "isBestFriend": true
    },
    {
      "name": "小雨",
      "email": "xiaoyu@example.com",
      "avatar": "",
      "persona": "温柔细心的女生，总是第一个安慰人",
      "activity": 60,
      "likeRate": 0.4,
      "isBestFriend": false
    }
  ]
}
字段说明
activity活跃度 0~100，该角色对每帖回复的概率
likeRate刷到但没回复时，点赞（发 [LIKE] 评论）的概率
isBestFriend挚友标记：该角色每帖必回复（≥1 保证）
persona人设 prompt，喂给 LLM 的 system 消息

6. 行为流程（状态机）

6.1 单帖生命周期

  1. 轮询 sitemap 发现新帖 → 记录 page_key，给每个角色排一个随机"刷到时刻"
  2. 到点"刷到"：按活跃度决定行为——回复 / 只点赞 / 忽略；挚友跳过判定直接回复
  3. 回复前组装上下文：人设 + 帖子内容 + 当前完整评论串（含人工和其他 AI）
  4. LLM 生成口语化评论 → 以角色昵称/头像 POST 到 Artalk
  5. 该角色后续被其他评论"提到/接话"时，若 cascade 轮次未超限，可再回一条

6.2 状态字段（ai-state.json）

{
  "posts": {
    "posts/hello-world.html": {
      "seenAt": "2026-08-25T10:00:00+08:00",
      "characters": {
        "阿伟": { "status": "replied", "commentId": 123, "at": "..." },
        "小雨": { "status": "liked",   "commentId": 124, "at": "..." },
        "阿明": { "status": "skipped", "at": "..." }
      },
      "cascadeRound": 1
    }
  }
}

状态含"已处理"标记，配合 Artalk 侧按 page_key+昵称查重，双保险防重复评论。

7. 接口契约

接口方法 / 路径用途
Artalk 评论列表GET {server}/api/v2/comments?page_key=...拉取帖子评论作为上下文
Artalk 发布评论POST {server}/api/v2/commentsAI 评论（昵称/邮箱/内容/page_key）
LLMPOST {endpoint} chat/completions生成回复；system=人设，user=上下文
站点 sitemapGET {siteUrl}/sitemap.xml发现新帖
LLM 请求体为 OpenAI 兼容格式：{"model":..., "messages":[...], "temperature":...}。换成任意兼容服务只需改 endpoint/key/model。

8. 拟人参数

参数默认拟人作用
刷到延迟30 分钟 ~ 24 小时不秒回，模拟刷手机时机
活跃度按角色配置高频稳定出现，低频偶尔冒泡
点赞率按角色配置只点赞不评论的"潜水党"
缺席概率1 - activity不是每条都回，像真人
cascade 轮次≤2 轮AI-AI 接话聊几句自然冷场
人工评论参与率30%（可关）AI 会加入真人讨论
每帖软上限8 条防角色池大时刷屏

9. 错误处理与幂等

  • LLM 超时/失败：跳过该角色本次动作，记录日志，下次轮询再判定，不重试轰炸
  • Artalk 不可达：记日志，状态不推进，下轮重试
  • 重复评论：状态标记 + 发布前按 page_key+昵称查询去重
  • 进程崩溃：state 每次变更原子写盘，重启后从未完成动作继续
  • LLM 输出异常：截断超长内容、剥离 Markdown 残留、空输出重试一次后放弃

10. 测试计划

  • Mock 模式：配置文件加 mock: true——LLM 返回模板句，Artalk 操作只打日志不发真评论，用于本地全流程验证
  • 单元测试：概率判定（活跃度/点赞/缺席）、状态机流转、上下文拼装、JSON 幂等
  • 分布模拟：跑 1000 帖模拟，验证每帖 ≥1 条（挚友）、高频角色出现率贴近配置值
  • 集成验证：部署后先用 mock 观察一轮，再开真 LLM，观察 3~7 天调参（延迟、活跃度、参与率）

11. 明确不做（YAGNI）

  • 不做 AI 标识 / 评论角标（完全伪装）
  • 不做管理面板 UI（改配置即可）
  • 不做多站点管理
  • 不做"AI 发帖"（只评论，不替你发朋友圈）
  • 主题代码零改动、不新增任何 UI 组件，除非未来主动要求视觉区分
